# RUCH — Question Numbering Strategy

## 1. Overview

RUCH (Read. Understand. Code. Hone.) organizes interview questions into chapters.

Each question has two identifiers:

1. A system-generated database ID.
2. An administrator-assigned display number within its chapter.

This document defines how question numbers are assigned, validated, updated, ordered, and preserved during content lifecycle operations.

The strategy must support:

- Stable question identity.
- Chapter-specific numbering.
- Administrator-controlled organization.
- Database-enforced uniqueness.
- Safe concurrent creation.
- Question archival and restoration.
- Deterministic ordering.
- Compatibility with the existing REST API and relational schema.

## 2. Final Design Decision

RUCH uses **administrator-assigned question numbering**.

When creating a question, the administrator explicitly supplies its display number.

The backend does not automatically calculate or assign the next question number.

Example:

```json
{
  "questionNumber": 15,
  "questionText": "What is polymorphism in Java?",
  "referenceAnswer": "Polymorphism allows objects to take multiple forms."
}
```

The backend validates the request and persists the number if it is available within the selected chapter.

The database remains the final authority for uniqueness.

## 3. Question ID vs. Question Number

### 3.1 Question ID

The `id` column is the permanent technical identifier.

```sql
id BIGINT NOT NULL AUTO_INCREMENT
```

Properties:

- Generated by MySQL.
- Globally unique across all questions.
- Used as the primary key.
- Used by foreign keys and REST resource URLs.
- Never changes when a question is renumbered.
- Never changes when a question is archived or restored.

Example:

```http
GET /api/v1/questions/103
```

### 3.2 Question Number

The `question_number` column represents the administrator-defined display order.

```sql
question_number INT NOT NULL
```

Properties:

- Assigned by the administrator.
- Must be a positive integer.
- Unique within its chapter.
- May be repeated in different chapters.
- May change through an authorized administrative update.
- Is not used as a foreign key for learner progress or revision history.

### 3.3 Example

| id | chapter_id | question_number | Question |
|---|---|---|---|
| 101 | 1 | 1 | What is JVM? |
| 102 | 1 | 2 | What is JDK? |
| 103 | 1 | 3 | What is JRE? |
| 104 | 2 | 1 | What is Spring Boot? |
| 105 | 2 | 2 | What is dependency injection? |

Question number 1 can exist in both chapters because numbering is scoped to the chapter.

Question IDs remain globally unique.

## 4. Database Constraints

The `questions` table uses the following relevant columns and constraints:

```sql
CREATE TABLE questions (
    id BIGINT NOT NULL AUTO_INCREMENT,
    chapter_id BIGINT NOT NULL,
    question_number INT NOT NULL,
    question_text VARCHAR(2000) NOT NULL,
    reference_answer TEXT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'DRAFT',
    created_at DATETIME(6) NOT NULL,
    updated_at DATETIME(6) NOT NULL,

    PRIMARY KEY (id),

    CONSTRAINT fk_questions_chapter
        FOREIGN KEY (chapter_id)
        REFERENCES chapters(id)
        ON DELETE RESTRICT,

    CONSTRAINT uk_questions_chapter_number
        UNIQUE (chapter_id, question_number),

    CONSTRAINT chk_questions_number
        CHECK (question_number > 0),

    CONSTRAINT chk_questions_status
        CHECK (status IN ('DRAFT', 'PUBLISHED', 'ARCHIVED')),

    CONSTRAINT chk_questions_text
        CHECK (CHAR_LENGTH(TRIM(question_text)) > 0),

    CONSTRAINT chk_questions_answer
        CHECK (CHAR_LENGTH(TRIM(reference_answer)) > 0)
) ENGINE=InnoDB;
```

This is the relevant `questions` table definition from the database design. It must not be executed as a second `CREATE TABLE` statement after the Ticket 11 schema has already been applied.

### 4.1 Composite Unique Constraint

```sql
CONSTRAINT uk_questions_chapter_number
    UNIQUE (chapter_id, question_number)
```

This prevents duplicate question numbers within a chapter.

Examples:

| chapter_id | question_number | Valid? |
|---|---|---|
| 1 | 1 | Yes |
| 1 | 2 | Yes |
| 2 | 1 | Yes |
| 1 | 2 again | No |

### 4.2 Positive Number Constraint

```sql
CHECK (question_number > 0)
```

Zero and negative numbers are invalid.

The request DTO must also validate the value before reaching the persistence layer.

### 4.3 Foreign Key

```sql
FOREIGN KEY (chapter_id)
REFERENCES chapters(id)
```

The question must belong to an existing chapter.

The chapter ID is supplied through the creation endpoint path rather than the JSON request body.

## 5. Question Creation Contract

### 5.1 Endpoint

```http
POST /api/v1/admin/chapters/{chapterId}/questions
```

Requires the `ADMIN` role.

### 5.2 Request

```json
{
  "questionNumber": 15,
  "questionText": "What is polymorphism?",
  "referenceAnswer": "Polymorphism allows objects to take multiple forms."
}
```

### 5.3 Request DTO

```java
public record CreateQuestionRequest(

        @NotNull
        @Positive
        Integer questionNumber,

        @NotBlank
        @Size(max = 2000)
        String questionText,

        @NotBlank
        @Size(max = 20000)
        String referenceAnswer

) {}
```

### 5.4 Validation Rules

| Field | Required | Validation |
|---|---|---|
| `questionNumber` | Yes | Positive integer |
| `questionText` | Yes | Not blank, maximum 2,000 characters |
| `referenceAnswer` | Yes | Not blank, maximum 20,000 characters |

Additional rules:

- The chapter must exist.
- The chapter must be eligible for question creation.
- The number must not already be assigned to another question in the chapter.
- The client cannot supply the database question ID.
- The client cannot supply the initial publication status.
- New questions start in `DRAFT`.

### 5.5 Successful Response

HTTP status: `201 Created`.

```json
{
  "id": 106,
  "chapterId": 1,
  "questionNumber": 15,
  "questionText": "What is polymorphism?",
  "referenceAnswer": "Polymorphism allows objects to take multiple forms.",
  "status": "DRAFT"
}
```

The response includes both the permanent ID and the display number.

## 6. Concurrent Question Creation

### 6.1 Problem

Two requests may attempt to create question number 21 in the same chapter simultaneously.

Example:

```text
Request A:
chapterId = 1
questionNumber = 21

Request B:
chapterId = 1
questionNumber = 21
```

Both requests may pass an application-level availability check before either transaction commits.

An application-level `existsByChapterIdAndQuestionNumber` check is therefore not sufficient to guarantee uniqueness.

### 6.2 Database Protection

The composite unique constraint guarantees that two committed rows cannot share the same `(chapter_id, question_number)` pair.

Under normal successful database operation:

- One conflicting insert may succeed.
- The other is rejected by MySQL.
- The rejected request is mapped to a domain-specific API conflict.

The backend must not assume which request wins.

### 6.3 Service Behavior

The question creation service should:

1. Validate the request DTO.
2. Validate chapter existence and eligibility.
3. Optionally check whether the requested number already exists to provide an early error.
4. Attempt the insert.
5. Allow the database unique constraint to enforce the final invariant.
6. Translate a violation of `uk_questions_chapter_number` into a consistent API error.

The application must distinguish this named unique-constraint violation from unrelated database failures.

### 6.4 Duplicate Number Error

HTTP status:

```http
409 Conflict
```

Example response:

```json
{
  "timestamp": "2026-11-11T15:30:00Z",
  "status": 409,
  "error": "CONFLICT",
  "code": "QUESTION_NUMBER_ALREADY_EXISTS",
  "message": "Question number 21 already exists in this chapter",
  "path": "/api/v1/admin/chapters/1/questions",
  "requestId": "req-12345",
  "fieldErrors": [
    {
      "field": "questionNumber",
      "message": "This question number is already assigned in the selected chapter"
    }
  ]
}
```

This extends Ticket 10's standard error-code catalog.

### 6.5 Retry Policy

The backend must not silently change an administrator-assigned question number.

For example, if number 21 is occupied, the backend must not automatically assign number 22.

The administrator must choose a different number and submit a new request.

Automatic retries that preserve the conflicting number are not useful for a permanent uniqueness conflict.

### 6.6 Transaction Considerations

Normal database transactions and the composite unique constraint are sufficient to protect uniqueness during independent question creation requests.

An additional chapter-level allocation lock is unnecessary because the backend does not generate sequential question numbers.

More complex administrative operations, such as swapping question numbers, may require transaction-level coordination.

## 7. Question Renumbering

### 7.1 Endpoint

```http
PATCH /api/v1/admin/questions/{questionId}
```

### 7.2 Request

```json
{
  "questionNumber": 25
}
```

### 7.3 Rules

- Only administrators can renumber questions.
- The new number must be positive.
- The number must be available within the same chapter.
- Omitted fields remain unchanged.
- Explicit null values are rejected.
- The question ID remains unchanged.
- Learning progress and revision history remain associated with the same question ID.
- Renumbering does not modify historical revision records.

### 7.4 Conflict Handling

If the requested number is already assigned to another question in the same chapter, return:

```http
409 Conflict
```

with code:

```text
QUESTION_NUMBER_ALREADY_EXISTS
```

### 7.5 Swapping Numbers

Suppose:

```text
Question A = 10
Question B = 11
```

Directly changing A to 11 violates the unique constraint.

The MVP does not require a dedicated atomic swap or bulk-reordering API.

Administrators can use an available temporary positive number and perform controlled sequential updates.

For example:

```text
A: 10 → 100
B: 11 → 10
A: 100 → 11
```

This sequence is not atomic across multiple independent API calls. If interrupted, an intermediate numbering state may remain.

A future bulk-reordering endpoint should use a single transaction with an explicit concurrency strategy.

## 8. Question Archiving

### 8.1 Archive Operation

Endpoint:

```http
POST /api/v1/admin/questions/{questionId}/archive
```

Archiving changes the question status to `ARCHIVED`.

It does not delete the question row.

### 8.2 Number Preservation

An archived question retains:

- Its database ID.
- Its chapter ID.
- Its question number.
- Its question text and reference answer.
- Its associated learner progress.
- Its revision history.

### 8.3 Example

Before archival:

| Question ID | Number | Status |
|---|---|---|
| 101 | 1 | PUBLISHED |
| 102 | 2 | PUBLISHED |
| 103 | 3 | PUBLISHED |

After archiving question 102:

| Question ID | Number | Status |
|---|---|---|
| 101 | 1 | PUBLISHED |
| 102 | 2 | ARCHIVED |
| 103 | 3 | PUBLISHED |

The learner sees question numbers 1 and 3.

The backend does not renumber question 3 to 2.

### 8.4 Number Reuse

Archived question numbers remain reserved.

A new question cannot reuse number 2 in that chapter while the archived question retains it.

This is enforced by the composite unique constraint because it applies to all rows, regardless of publication status.

### 8.5 Restoration

Restoring an archived question changes its status to `DRAFT`.

The question retains its original number.

An administrator must explicitly publish it again.

Restoration does not recreate learner progress or revision history because those records were never deleted.

## 9. Chapter Archiving

Archiving a chapter does not change the question numbers of its associated questions.

Questions remain associated with the chapter through `chapter_id`.

The chapter is excluded from active learner views.

Restoring the chapter does not renumber its questions.

The administrator controls subsequent publication.

## 10. Deterministic Question Ordering

### 10.1 Default Ordering

Questions are ordered by:

```sql
ORDER BY question_number ASC, id ASC
```

The unique `(chapter_id, question_number)` constraint already prevents duplicate numbers within a chapter.

The ID is included as an additional deterministic tie-breaker.

### 10.2 Example Query

```sql
SELECT
    id,
    chapter_id,
    question_number,
    question_text
FROM questions
WHERE chapter_id = ?
  AND status = 'PUBLISHED'
ORDER BY question_number ASC, id ASC;
```

The service must also verify that the parent chapter is published before exposing learner-facing results.

### 10.3 Pagination

For paginated question lists:

```sql
ORDER BY question_number ASC, id ASC
LIMIT ? OFFSET ?;
```

The ordering must be applied consistently across all pages.

Offset pagination is sufficient for the MVP, although concurrent insertions or renumbering between separate page requests can shift page boundaries.

### 10.4 Gaps

Question numbering is not required to be contiguous.

Valid chapter numbering:

```text
1, 2, 5, 10, 15
```

The backend must not automatically fill gaps.

The frontend must display the stored `questionNumber`, not calculate a display number from the array index or pagination offset.

## 11. Angular Administrator Experience

The Angular admin form includes a required Question Number input.

Example:

```text
Chapter: Java Fundamentals

Question Number: [15]

Question Text:
[What is polymorphism?]

Reference Answer:
[Polymorphism allows objects...]

[Create Question]
```

### 11.1 Frontend Validation

Angular reactive forms validate:

- Question number is required.
- Question number is a positive integer.
- Question text is required.
- Reference answer is required.

Backend validation remains authoritative.

### 11.2 Duplicate Number Feedback

When the backend returns:

```text
QUESTION_NUMBER_ALREADY_EXISTS
```

Angular displays the error next to the Question Number field.

Example:

```text
Question number 15 is already assigned in this chapter.
```

The administrator can change the number and retry.

### 11.3 Optional Number Suggestion

A future enhancement may suggest the next available number.

Such a suggestion is informational only.

It does not reserve a number and cannot guarantee availability during concurrent creation.

The MVP does not require a separate number-suggestion endpoint.

## 13. Database Schema Alignment

Ticket 11 already defines:

```sql
question_number INT NOT NULL
```

and:

```sql
CONSTRAINT uk_questions_chapter_number
    UNIQUE (chapter_id, question_number)
```

No structural change to the Ticket 11 `questions` table is required for this strategy.

The Ticket 12 design clarifies the assignment and lifecycle rules for these existing columns.

## 14. Testing Requirements

### 14.1 Identity Tests

- Question ID is generated by MySQL.
- Question ID remains unchanged after renumbering.
- Question ID remains unchanged after archival and restoration.

### 14.2 Chapter Scope Tests

- Chapter 1 can contain Question 1.
- Chapter 2 can independently contain Question 1.
- Chapter 1 cannot contain two questions numbered 1.

### 14.3 Validation Tests

- Missing question number returns 400.
- Zero returns 400.
- Negative numbers return 400.
- Non-integer values return 400.
- Duplicate numbers return 409.

### 14.4 Concurrency Tests

- Two simultaneous inserts with the same chapter and number cannot both succeed.
- The database unique constraint prevents duplicate committed records.
- The losing request receives the documented conflict response.
- Two requests using the same number in different chapters may both succeed.

### 14.5 Archiving Tests

- Archiving retains the original number.
- Archived numbers cannot be reused.
- Restoring retains the original number.
- Other questions are not automatically renumbered.
- Learning progress and revision history remain intact.

### 14.6 Ordering Tests

- Questions are returned in ascending question-number order.
- Gaps do not affect ordering.
- Pagination uses the documented deterministic order.
- Renumbering changes display order without changing question identity.

### 14.7 Authorization Tests

- Learners cannot create questions.
- Learners cannot renumber questions.
- Learners cannot archive or restore questions.
- Administrators can perform authorized numbering operations.

## 15. Final Design Decisions

RUCH adopts the following numbering rules:

1. Every question has a globally unique, immutable database ID.
2. Every question has an administrator-assigned display number.
3. Display numbering is scoped to a chapter.
4. Question numbers must be positive integers.
5. The database enforces `UNIQUE (chapter_id, question_number)`.
6. The backend does not automatically allocate question numbers.
7. Concurrent duplicate creation is resolved by the database constraint.
8. Duplicate numbering conflicts return HTTP 409.
9. The backend never silently changes a requested number.
10. Administrators may explicitly renumber questions through PATCH.
11. Renumbering does not modify question IDs or learner history.
12. Archived questions retain their numbers.
13. Archived numbers remain reserved.
14. Restored questions retain their previous numbers.
15. Numbering gaps are permitted.
16. Learner question lists use `question_number ASC, id ASC`.
17. Angular displays stored question numbers rather than generating them.
18. Bulk atomic reordering is deferred beyond the MVP.

This strategy provides stable question identity, predictable ordering, administrator-controlled content organization, and reliable database-level protection against duplicate question numbers.
